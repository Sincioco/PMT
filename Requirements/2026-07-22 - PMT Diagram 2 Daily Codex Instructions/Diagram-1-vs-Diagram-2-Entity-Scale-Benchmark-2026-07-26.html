Result

Diagram 1 became unusable at 3 entities under the current full PMT diagram library state. Diagram 2 completed the progressive ladder through 3,000 entities without reaching the 20-second cap.

The Diagram 1 result is severe because the screen does more than render the selected diagram: it also builds the legacy Diagram library and read-only SVG path in a way that blocks the browser main thread. Diagram 2 keeps the selected document path isolated and uses the new renderer diagnostics, low-detail overview, and keyed SVG rendering.

Why Diagram 1 Fails Earlier

  • Legacy screen work blocks the main thread. Diagram 1 does heavyweight read-only SVG hydration and library work in the same browser context, so small selected diagrams can still suffer when the library contains very large saved diagrams.
  • Full SVG rebuilds dominate. Diagram 1 parses saved annotation metadata and rebuilds a rich SVG tree instead of keeping a renderer-owned canonical state with keyed node maps.
  • No renderer-local idle contract. Diagram 1 has no equivalent to window.__pmtDiagram2Renderer.whenIdle(), so the UI can appear visible while the main thread is still saturated.
  • No practical large-diagram scaling path. Without low-detail overview and selective renderer diagnostics, the legacy path has no clean way to degrade gracefully as entity and relationship counts rise.

Why Diagram 2 Scales Better

  • Canonical model first: Diagram 2 reads the same saved Diagram metadata but renders from normalized state instead of treating the saved SVG as the live editor surface.
  • Keyed SVG rendering: Objects and relationships are tracked by stable IDs, allowing the renderer to update nodes predictably.
  • Low-detail overview: From 100 entities upward in these runs, Diagram 2 used low-detail overview mode, reducing field-row detail that cannot be read at fit scale.
  • Explicit diagnostics: The renderer reports canonical counts, mounted counts, route sectors, frame time, detail mode, and halo coverage, making performance measurable instead of anecdotal.
  • Isolation from Diagram 1: Diagram 2 is a separate top-level route and renderer, so it does not inherit the legacy read-only SVG lifecycle.

Methodology

  • Browser: Playwright Chromium, authenticated as Sin against http://127.0.0.1:5056.
  • Each measurement starts after login; timing begins when the hash route changes.
  • Diagram 1 ready condition: selected read-only Diagram SVG visible and not busy.
  • Diagram 2 ready condition: selected Diagram 2 SVG visible and whenIdle() resolved.
  • Each individual run used a 20.00 s practical cap. Every shell command was kept below one minute.
